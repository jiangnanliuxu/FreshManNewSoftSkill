# 软件开发引导型 Skill Harness 设计文档

## 0. 文档定位

本文档用于设计一个可控的 LLM Skill Harness。它不是普通的软件开发流程说明，而是一个给 LLM 执行的软件开发控制框架。

Harness 的目标：

```text
把用户从 0 基础软件想法，引导到需求、设计、开发、测试、上线准备和最终交付；
同时通过状态文件、阶段路由、Agent 合约、权限表、门禁、异常处理和回滚机制，
降低 LLM 自作主张、跳步骤、状态丢失、重复开发、漏测、乱改文件的风险。
```

核心思想：

```text
用户意图 -> Harness 读取状态 -> 选择模式 -> 路由阶段 -> 调度 Agent -> 写入文档 -> 校验门禁 -> 进入下一步
```

本文档后续可拆分成真正 Skill 的：

```text
SKILL.md
references/harness.md
references/document-schemas.md
references/agent-contracts.md
references/testing-rules.md
```

## 1. Skill 触发合约

### 1.1 推荐 Skill 名称

```yaml
name: software-dev-guide
description: Guide beginner or non-technical users through a document-driven, multi-agent software development lifecycle. Use when the user wants to build software, a website, app, mini program, backend system, dashboard, automation tool, course project, or digital product and needs controlled step-by-step requirements analysis, product design, module planning, development, interruption recovery, change handling, testing, rollback, release preparation, or final delivery documentation.
```

### 1.2 触发后第一原则

Skill 触发后，主 Agent 不允许直接开始写代码。必须先执行 Harness 入口流程：

```text
1. 判断用户意图。
2. 判断是否已有项目目录和 docs 文档。
3. 判断复杂度模式。
4. 读取或创建项目状态文件。
5. 检查是否存在未确认门禁、异常、回滚、未完成模块。
6. 决定进入哪个阶段。
```

### 1.3 用户常见意图路由

| 用户说法                       | Harness 路由 |
| ------------------------------ | ------------ |
| 我想做一个软件 / 网站 / 小程序 | 新项目入口   |
| 继续开发 / 接着做              | 恢复开发入口 |
| 我有新需求 / 加一个功能        | 需求变更入口 |
| 这个需求不要了 / 回到之前      | 回滚撤销入口 |
| 状态不对 / 文档不对 / 测试不对 | 异常处理入口 |
| 帮我测试                       | 测试入口     |
| 准备上线                       | 上线准备入口 |
| 帮我整理交付文档 / 我要交作业  | 最终交付入口 |

## 2. Harness 总控制循环

### 2.1 主循环

每轮对话都按这个顺序执行：

```text
Step 1: ParseIntent
识别用户当前意图：新项目 / 继续开发 / 新需求 / 回滚 / 测试 / 上线 / 交付 / 提问。

Step 2: LoadState
读取 docs/00-项目状态总览.md；如果没有，创建最小状态。

Step 3: SelectMode
判断轻量 / 标准 / 严格模式；如果已有模式，沿用，除非触发升级。

Step 4: ValidateGuards
检查用户确认门禁、模块锁、异常记录、回滚记录、追踪矩阵、任务看板。

Step 5: RouteStage
根据状态和用户意图进入阶段 1 到阶段 7 或特殊入口。

Step 6: DispatchAgent
主 Agent 决定是否调度 A/B/C Agent，或由主 Agent 按角色执行。

Step 7: ExecuteOneUnit
一次只推进一个明确单元：一个问题组、一个模块、一个测试批次、一个变更、一个交付包。

Step 8: Persist
所有结论写入对应文档，不依赖聊天记忆。

Step 9: Report
向用户输出当前阶段、已完成、下一步、需要确认的问题。
```

### 2.2 一次只推进一个最小工作单元

为了让 LLM 可控，禁止“一口气从需求做到上线”。每轮只能推进一个最小单元：

```text
需求阶段：最多一组 3 到 5 个问题。
设计阶段：最多确认一个核心流程或一组页面。
开发阶段：最多开发一个模块。
测试阶段：最多测试一个模块或一个变更批次。
变更阶段：最多处理一个 CR。
回滚阶段：最多处理一个 RB。
交付阶段：最多生成或更新一个交付包。
```

### 2.3 主 Agent 每轮固定输出

```text
当前模式：
当前阶段：
读取到的状态：
本轮执行：
写入 / 更新的文档：
阻塞项：
下一步：
需要用户确认：
```

## 3. 复杂度模式 Harness

### 3.1 模式定义

| 模式     | 适用项目                                 | 控制强度               |
| -------- | ---------------------------------------- | ---------------------- |
| 轻量模式 | 单页面、小作业、静态网页、无后端         | 少文档、快速推进       |
| 标准模式 | 课程设计、小程序、后台管理、带数据功能   | 文档完整、适度控制     |
| 严格模式 | 真实上线、多角色权限、敏感数据、频繁变更 | 全门禁、全日志、全追踪 |

### 3.2 模式选择规则

主 Agent 根据以下规则初判：

```text
页面 1 到 3 个、无登录、无数据库：轻量模式。
有数据库、多个页面、课程设计、小程序：标准模式。
有真实上线、多角色权限、敏感数据、支付、文件上传、频繁变更：严格模式。
```

用户可以要求切换模式，但：

```text
降低模式会减少控制文档，必须经过用户确认门禁。
升级模式可以由主 Agent 主动建议。
严格模式降级必须记录原因。
```

## 5. Agent Harness 合约

### 5.1 主 Agent 合约

职责：

```text
读取状态
选择模式
路由阶段
调度 A/B/C Agent
维护门禁
处理异常
处理回滚
总结进度
决定是否进入下一阶段
```

禁止：

```text
未读状态就继续开发
未确认 MVP 就进入开发
未确认技术栈就创建项目
测试不通过仍直接上线
隐藏未完成事项
跳过文档写入
```

### 5.2 A Agent 合约

职责：

```text
向用户提问
整理需求
拆解 P0/P1/P2
设计页面和流程
定义 UI/交互验收标准
维护需求变更记录中的产品部分
输出 A -> B 交接包
```

禁止：

```text
直接修改代码
直接改开发日志
擅自决定新需求插队
把模糊需求交给 B Agent
```

### 5.3 B Agent 合约

职责：

```text
读取需求、设计、技术方案
拆分模块
开发代码
检查模块完整度
保存开发日志
更新任务看板和追踪矩阵
输出 B -> C 交接包
恢复开发时核对日志和代码
```

禁止：

```text
开发未拆分需求
开发未确认 P0 范围
绕过模块锁
擅自修改验收标准
开发完不写日志
开发完不交测试
```

### 5.4 C Agent 合约

职责：

```text
读取需求、设计、开发日志、追踪矩阵、UI 验收标准
生成测试计划
生成测试用例
执行功能、异常、构建、回归、UI/交互测试
写测试报告
输出 C -> 主 Agent 交接包
```

禁止：

```text
直接修改业务代码
测试未开发完成模块
忽略 P0 新需求
测试失败不记录缺陷
有条件通过不触发主 Agent 决策
```

## 7. 工具能力 Harness

### 7.1 工具能力定位

工具能力用于把容易出错、需要重复执行、需要稳定格式的动作从 LLM 自由发挥中抽离出来。Harness 里的工具分两类：

```text
脚本工具：放在 Skill 的 scripts/ 目录，例如初始化文档、校验状态、查找下一任务。
增强 MCP 能力：依赖用户 Codex 环境已接入的 MCP，例如 Stitch UI 生成能力。
```

原则：

```text
1. 工具是增强能力，不是所有项目的硬依赖。
2. 主 Agent 使用工具前必须先检测能力是否可用。
3. 工具不可用时，必须提供降级流程。
4. 工具输出必须写入 Harness 文档，而不是只存在聊天记录。
5. 工具失败必须进入异常处理机制，不能静默跳过。
```

后续正式制作 Skill 时，建议在 `scripts/` 中创建这些工具：

#### init_project_docs.py

用途：

```text
根据复杂度模式创建 docs/ 文档骨架。
轻量模式创建最小文档集。
标准模式创建完整核心文档集。
严格模式创建全部门禁、追踪、异常、回滚、交付文档。
```

输入参数建议：

```text
--project-path 项目路径
--mode light|standard|strict
--project-name 项目名称
--project-type 项目类型
--force 是否覆盖已有模板，默认 false
```

输出：

```text
创建的文档列表
跳过的已有文档列表
初始化后的 docs/00-项目状态总览.md 摘要
```

失败处理：

```text
项目路径不存在：提示主 Agent 先确认路径。
docs 已存在：默认不覆盖，除非用户确认。
写入失败：进入异常处理机制。
```

#### validate_harness_state.py

用途：

```text
校验 Harness 文档之间的状态一致性。
检查任务看板、状态总览、追踪矩阵、测试报告、门禁、异常、回滚是否冲突。
```

检查项：

```text
状态总览中的当前模块是否存在于任务看板。
P0 需求是否都有模块ID和测试用例ID。
开发完成但未测试的模块是否被标记为待测试。
测试失败模块是否进入待修复。
是否存在未确认门禁。
是否存在未解决异常。
是否存在未验证回滚。
是否存在未释放模块锁。
```

输入参数建议：

```text
--project-path 项目路径
--mode light|standard|strict
--format text|json
```

输出：

```text
校验结论：pass|warning|fail
问题列表
建议下一步
```

#### find_next_task.py

用途：

```text
根据状态总览、任务看板、追踪矩阵、门禁、异常记录和回滚记录，找出下一步应该做什么。
```

优先级规则：

```text
1. 未解决异常
2. 未验证回滚
3. 必须确认但未确认的门禁
4. 阻塞级测试缺陷
5. P0 新需求
6. 当前 P0 模块未完成部分
7. 待测试模块
8. P1 模块或优化
9. 最终交付包
```

输入参数建议：

```text
--project-path 项目路径
--format text|json
```

输出：

```text
next_action：ask_user|dispatch_a|dispatch_b|dispatch_c|handle_exception|handle_rollback|prepare_delivery
target_module：
target_doc：
reason：
blocking_items：
```

### 7.3 Stitch UI 增强能力

Stitch UI 是阶段 3 产品设计的增强能力，用于生成更专业的前端 UI 页面或原型。它不是硬依赖。

Stitch 可用时：

```text
主 Agent 可以通过 Stitch MCP 创建项目、生成页面、读取 screen 信息。
A Agent 将 Stitch 页面转成产品页面说明和 UI/交互验收标准。

C Agent 根据 Stitch 设计做 UI/交互验收。
```

Stitch 不可用时：

```text

```

### 7.4 Stitch 可用性检测

用户选择 Stitch 后，主 Agent 必须先检测能力：

```text
1. 检测当前环境是否存在 Stitch MCP 工具。
2. 如果存在，调用 list_projects 或 create_project 做轻量验证。
3. 如果可用，进入 Stitch UI 子流程。
4. 如果不可用，进入 Stitch 连接引导或降级流程。
5. 如果用户不想连接，回到 Codex 原生 UI 设计流程。
```

Stitch MCP 可能包含的能力：

```text

edit_screens
generate_variants
list_projects
list_screens
get_project

apply_design_system
```

### 7.5 Stitch UI 子流程

```text
1. 主 Agent 创建用户确认门禁：是否使用 Stitch 增强设计。
2. A Agent 把需求、页面、角色、风格要求整理成 Stitch Prompt。
3. 主 Agent 调用 Stitch MCP 创建项目或生成页面。
4. 用户在 Stitch 中查看和调整设计。
5. 用户说“我改好了”后，主 Agent 通过 MCP 读取项目和 screen。
6. A Agent 将 Stitch 页面转成 docs/02-产品页面与业务流程.md。
7. A Agent 将 UI 要求写入 docs/15-UI交互验收标准.md。
8. 主 Agent 将 Stitch 项目ID、screenID、更新时间写入协同事件日志。
9. B Agent 根据设计文档开发前端。
10. C Agent 根据 Stitch 设计和 UI 验收标准测试。
```

```text
阻塞 / 高 / 中 / 低
```

### 18.4 测试结论规则

| 结论       | 条件                          | 下一步                 |
| ---------- | ----------------------------- | ---------------------- |
| 通过       | P0 用例全部通过，无高风险问题 | 进入下一模块或上线准备 |
| 有条件通过 | 仅低风险问题，且不影响 P0     | 触发用户确认门禁       |
| 不通过     | 存在高风险或阻塞问题          | 回流 B Agent 修复      |

## 19. 异常处理 Harness

### 19.1 触发条件

```text
文档和代码不一致。
任务看板和测试报告不一致。
追踪矩阵断链。
模块锁残留。
Agent 越权修改文件。
测试结果与实际不一致。
用户指出“不是这样”。
```

### 19.2 异常处理流程

```text
1. 主 Agent 暂停当前推进。
2. 写入 docs/13-异常处理记录.md。
3. 判定异常来源。
4. 指派 A/B/C 核对各自主责内容。
5. 给出修复方案。
6. 如影响范围或上线风险，触发用户确认门禁。
7. 修复后更新状态、看板、矩阵、事件日志。
8. 恢复原流程。
```

## 22. 最终响应 Harness

### 22.1 每轮用户可见响应

主 Agent 每轮给用户的响应必须短而明确：

```text
我已经读取到当前项目处于【阶段 5：开发中】，当前模块是 M1：首页与导航。
本轮我会让 B Agent 继续完成 M1 的空状态和按钮交互，并把日志写入 docs/05-开发日志.md。
当前没有未确认门禁；如果开发中发现状态冲突，会先进入异常处理。
```

### 22.2 完成一轮后的响应

```text
本轮完成：
更新文档：
当前状态：
下一步：
需要你确认：
```

### 22.3 禁止输出

```text
不要只说“已完成”，必须说明完成了什么。
不要说“应该可以”，必须基于测试或文档状态。
不要隐藏遗留问题。
不要跳过用户确认门禁。
不要在无项目路径时假装已经修改代码。
```
